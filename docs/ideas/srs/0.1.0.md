## 1. 시스템 경계와 실행 전제

FastAPI 기반 `orchestrator`의 코어가 STT → 작업 처리 → TTS를 제어한다. 웹과 HT813 FXO 발신·착신 채널은 [공통 계약](../../../apps/orchestrator/src/voice_agent/contracts/)으로 변환하며 코어 내부 또는 서로의 구현을 직접 호출하지 않는다. `llm.example.test`은 작업 처리 대상이고 인증 비밀은 런타임에만 주입한다.

HT813 주소 `192.0.2.17`과 FXO SIP `5062/UDP`는 관리 화면의 관찰값이다. 실제 SIP 인증·양방향 RTP 경로·발신 번호 전달·착신 Caller ID·회선 점유 의미는 미검증이다. FXS 전화기는 미연결이다. 이 문서의 실장 수용 기준은 향후 별도 승인 Gate 1/2에 따른 통합 검증 대상으로 남긴다.

## 4. HT813 FXO 에이전트 발신 요구사항

|ID|요구사항|검증 기준|
|---|---|---|
|SRS-T01|발신 번호는 3~15자리 숫자와 선택적 선행 `+`로 제한한다. 비어 있지 않은 정확한 번호·접두사 허용 정책을 통과해야 한다. `*`·`#` 기능 코드는 거부한다.|미허용 번호, 형식 오류, 기능 코드에서는 SIP 발신 시도를 생성하지 않는다. 실제 허용 번호 목록은 운영자가 입력해야 한다.|
|SRS-T02|발신 채널은 HT813 FXO로 SIP 연결을 시도하고 dialing, ringing, active, busy, failed, ended를 이벤트로 낸다.|연결·점유·거절·시간 초과·정상 종료가 각각 상태로 구분된다. 답변 송출 뒤에는 SIP 연결을 유지하고 상대 사용자의 통화 종료 신호에서 정상 종료·자원 정리를 확인한다.|
|SRS-T03|연결된 한 통화에서 사용자의 발화를 여러 번 받아 각각 STT→작업 처리→TTS 음성 답변을 보낸다. 8 kHz 전화 음성을 내부 형식으로 변환하고 DTMF 숫자·기호·지속 시간을 보존한다.|같은 SIP 대화·세션 ID로 두 차례 이상 질의·음성 답변이 오가고 각 답변 뒤 통화가 유지된다. 협상된 코덱·RTP 포트·DTMF 전송 방식에서 청취 가능성과 숫자 전달을 확인한다.|
|SRS-T04|FXO 회선 사용 중 또는 다른 에이전트 세션 사용 중에는 새 발신을 거부한다. 통화 취소·상대 종료·네트워크 중단 후에는 채널이 다음 발신을 위해 정리된다.|fake 피어 단위 테스트와 승인된 실장 시험에서 발신 시도부터 상대 종료·정리까지 웹과 전화를 합친 활성 세션이 1개이며 중복 발신이 없다. 청취·작업 처리·합성 중 상대 종료에도 추가 음성 송출 없이 회선이 회수된다.|
|SRS-T05|한 발화의 종료와 SIP 통화 종료를 구분한다. 발화 종료 뒤에도 통화를 유지해 다음 발화를 받을 수 있으며, 정상 통화는 상대 사용자의 종료 신호로 끝난다.|무음 등 발화 경계로 첫 턴을 마친 뒤 같은 통화에서 다음 턴을 처리한다. 답변 후 자동 BYE가 없고 상대 종료 시 ended 상태와 자원 정리가 확인된다.|
|SRS-T06|후속 작업 요청에는 현재 통화의 최종 전사와 이전 최종 전사·에이전트 응답을 대화 순서대로 `llm.example.test/v1/chat/completions`의 `messages`로 보낸다. 이전 통화·부분 전사·음성 원본은 보내지 않는다.|첫 턴은 현재 최종 전사만, 둘째 턴부터는 같은 통화의 승인된 문맥만 전송한다. 문맥은 통화 종료 때 메모리에서 정리되며 다른 통화 요청·일반 로그에 남지 않는다. Bearer 인증과 재시도 0회는 유지한다.|

HT813의 현재 등록 상태 `Not Registered`는 직접 피어링 실패·성공의 판정 기준이 아니다. 인증 및 SIP 응답 매핑은 M5에서 공식 자료와 fake 피어로 구현하고 M6에서 실제 장비로 확인한다. 다중 턴·상대 종료 요구는 [ADR-007](../../records/3_decisions/ADR-007-ht813-multiturn-call-lifecycle.md)과 사용자의 M6 정정에 따라 추가했다. 기존 M5 단위 검증은 이 추가 요구를 증명하지 않는다. 기존 FXO 범위, 다중 턴 FXO, 전체 외부 착신 시나리오의 Gate 1은 M6 대화에서 각각 승인됐고, 2026-09-24 후속 지시에서 승인된 M6 범위의 Gate별 승인을 포괄 승인했다. 장비의 실제 설정 백업·변경 전/후·원복안은 별도 기술 선행조건이다.

|SRS-I02|에이전트 SIP 수신 경계는 설정된 HT813 피어의 착신만 받아들이고 타 출처 또는 잘못된 SIP/SDP 요청은 모델·작업 API 호출 전 거부한다. 이 피어 제한은 Caller ID 제한과 별개다.|가짜 피어에서 허용/미허용 출처, 잘못된 SDP, 중복 INVITE를 검증한다. 실제 HT813 SIP 주소·인증·코덱은 승인된 장비 시험에서 확인한다.|
|SRS-I03|외부 발신자가 건 하나의 SIP 통화에서 여러 최종 전사→작업→TTS 턴을 순서대로 처리한다. 답변 뒤 통화를 유지하며 발신자의 통화 종료 신호가 정상 종료 기준이다.|같은 통화·세션 ID로 최소 두 질의와 두 음성 답변을 완료하고 첫 답변 후 자동 BYE가 없으며 상대 종료 뒤 RTP/세션 점유가 해제된다. 후속 작업 API 전송 범위는 SRS-T06과 같다.|
|SRS-I04|웹 또는 다른 전화 통화가 활성 상태면 새 외부 착신을 중복 처리하지 않고 통화 불가 상태로 응답한다. 이때 FXS로 자동 분기하지 않는다.|동시 착신의 SIP 응답과 모델/API 호출 0회, 기존 통화의 연속성 및 종료 뒤 다음 통화 수락을 확인한다.|
|SRS-I05|착신 접근 정책 변경은 외부 발신 번호 허용 정책 SRS-T01을 완화하지 않는다.|미허용 외부 발신 번호는 계속 SIP 발신 패킷 0개이고, 착신에는 Caller ID 허용 목록을 사용하지 않는다.|
|SRS-I06|인증된 로컬 운영자는 `GET /operator/inbound-calls`로 새 AI 착신의 통화 ID, 시작·종료 시각, 상태, HT813가 SIP로 전달한 발신자 번호 전체 또는 `null`을 최신순·제한된 페이지로 조회한다. 번호는 신원 확인 결과가 아니다.|Caller ID 전송 방식(`From`/`P-Asserted-Identity`/`P-Preferred-Identity`)과 번호 없음·계정 ID 오인 방지, 무음 통화, 종료·중단, 정렬·페이지·인증 거부를 검증한다. 번호는 AES-GCM 아티팩트 안에만 있고 파일명·일반 로그·삭제 감사에는 없으며 생성 후 30일에 삭제된다. 기존 기록의 번호와 백엔드 중지 중 부재중 전화는 조회되지 않는다.|

외부 착신→에이전트는 사용자의 2026-09-24 M6 범위 정정이다. 제조사 문서는 PSTN 착신의 SIP 전달 설정을 설명하지만 현 장비와 앱의 SIP 수신·RTP 상호 운용성은 미검증이다. FXS 전화기는 미연결이며 외부 착신→FXS의 기존 로컬 경로는 이번 M6 착신 목적지에서 대체됐다. PRD-03에 추적한 착신 실장 Gate 1과 승인된 M6 범위의 Gate 2는 포괄 승인됐지만, 실제 장비 변경·실전화 전에 현 설정과 백업·원복 가능성을 확인해야 한다.

M4 계약 테스트는 장비·웹·작업 API의 통합 동작을 증명하지 않는다. 최초 M4 기준선의 Gate 1/2와 M5/M6 실행 상태는 당시 기록이며, M6에서 기존 웹·HT813 시나리오 Gate 1은 별도로 승인됐다. **다중 턴 FXO·전체 외부 착신·보존 경계 시나리오의 Gate 1은 각각 승인됐고, 사용자가 승인된 M6 범위의 Gate별 승인을 포괄 승인했다.** FXS 실장 시험은 이번 Phase에서 승인되지 않았으며, HT813 현 설정·백업·원복안이 없으면 장비 변경·실전화는 준비되지 않은 상태다.
