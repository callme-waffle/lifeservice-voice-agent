# 1. 개요

## A. 목표

**현재는 실제 전화 대화에 성공한 개발·실증 단계이며, 상시 서비스 개시 조건은 충족됐다고 판정할 수 없다.** 남은 중심 작업은 새 음성 코어 개발이 아니라 실제 발신 품질, 조회 기능의 운영 배포, 재부팅·장애·보존 복구, 반복 운영 검증이다. 개발자의 일시 기동 없이 착신에 응답하고, 운영자가 정확한 허용 번호에 발신하며, 통화 종료 후 내역과 대화를 조회할 수 있는 전화 우선 서비스를 만든다.

이번 문서는 현황 조사에 근거한 승인된 실행 계획이다. 단계별 검토·진행 승인은 아래 사용자 지정 MR 병합 게이트를 따른다. 문서 작성 완료와 서비스 개시 완료를 구분한다. 진행률 퍼센트는 산정하지 않는다. 구현·실장·배포·안정성의 분모가 다르기 때문이다.

## B. 범위

- 첫 서비스: 전체 FXO 착신→에이전트, 정확한 허용 번호 발신, 같은 통화의 연속 대화·상대 종료, 착신 목록·발착신 대화 조회.
- 초기 용량: 웹·전화를 합쳐 동시 활성 세션 1개, PSTN 회선 1개. Caller ID는 표시 정보이며 접근 인증 수단으로 쓰지 않는다.
- 운영자 사용: 기존 localhost Bearer API를 유지한다. 운영 호스트 또는 인증된 SSH 터널을 통해 발신·취소·착신 목록·대화 조회를 수행할 절차와 명령 예제를 제공한다. 토큰을 명령 이력·출력에 남기지 않는다.
- 배포 기준·키/데이터 복구·모델 캐시·장애 알림·품질 목표·릴리스 패키지·72시간 제한 운영까지 포함한다.
- root/component README, PRD/SRS, 운영 가이드, 실행 증거와 세션 정리도 WBS에 포함한다. PRD/SRS 수정은 문서별 독립 커밋으로 처리한다.
- 기존 M6 잔여 항목을 이 계획의 개시 게이트에 매핑한다. M7/M8 기능을 재구현하지 않으며 기존 계획을 임의로 대체·완료 처리하지 않는다. 각 구현 세션은 마일스톤 하나만 맡는다.

## C. 제외 범위 (Non-goals)

웹 사용자 화면, 공개 운영 API·외부 고객 계정/관리 UI, 다중 회선·다중 세션, 통화 전환, 녹음 다운로드, FXS 독립 발신, Asterisk/DB 도입, 신규 모델 학습은 첫 개시 범위에서 제외한다. FXS 진단 전화는 BUG-003 원인 분리에 필요한 경우 별도 범위로 다룬다. 물리 FXS가 회선을 공유한다면 사용 중 점유 충돌 자체는 첫 개시 전에 확인하거나 운영 중 동시 사용을 제한한다.

현재 작업 어댑터는 외부 chat completion 응답 텍스트를 받는다. 예약·주문·다른 시스템 변경 같은 업무 수행 성공이 구현됐다고 주장하지 않는다. 그러한 서비스 목적이 추가되면 별도 요구사항·도구 실행 계약·검증이 필요하다.

## D. 독립 세션·MR 승인·본 세션 관리 규칙 (2026-10-16 사용자 지정)

1. 본 채팅은 전체 계획 관리·단계 상태 취합·MR 병합 확인·후속 배정만 맡는다. M9~M12 구현·현장 검증을 직접 수행하지 않는다.
2. 마일스톤마다 사용자가 직접 리뷰 질문을 할 수 있는 독립 Codex 채팅 하나를 사용하고 그 채팅과 `.agents/sessions/<session-id>/STATUS.md`를 1:1로 연결한다. 디렉터리만 만들거나 내부 서브에이전트를 띄운 것을 독립 채팅 생성으로 간주하지 않는다.
3. 최초 M9 착수는 이번 명시 승인으로 허용한다. 다음 마일스톤은 선행 단계 결과 MR이 사용자에 의해 병합된 사실을 본 세션이 확인한 뒤 착수한다. MR은 현재 GitHub 저장소의 Pull Request를 뜻한다. 기본 대상은 기존 개발 기준 `dev/v0.0.1`이며 변경 시 명시한다. 에이전트는 직접 병합하거나 자동 병합을 설정하지 않는다.
4. 각 단계 담당자는 MR에 WBS별 완료 결과·검증 명령과 결과·미검증/잔여 위험·ADR/수용 기준·다음 실행 범위를 적는다. `MR 제출/리뷰 대기`, `검증 완료`, `사용자 병합 인수`를 서로 다른 상태로 관리한다. 미결정 설계는 제안 상태로 리뷰받고 사용자 병합으로 결정이 확인된 뒤 accepted로 추적한다.
5. 각 담당 세션에서 문서 조사·요구사항 대조·시험 설계·독립 코드 검토 등 서로 의존하지 않는 작업을 서브에이전트로 병렬화한다. 위임 전 표준 STATUS를 만들고 파일 소유권을 나눈다. 공용 파일·Git index·장비/키 조작·실전화는 담당자가 직렬 통합한다. WBS 선행조건을 병렬화 때문에 건너뛰지 않는다.
6. 단계 결과는 본 세션에 `단계/담당 채팅 ID/작업 브랜치/기준·결과 SHA/MR URL/검증/잔여 위험/사용자 필요 조치/다음 단계 조건`으로 회신한다. MR 병합 후 merge SHA·병합 주체·시각·검증 대상과 병합 head의 일치를 확인한다. 단순 PR close·리뷰 코멘트·approved review는 merge와 같지 않다.
7. 채팅 전달 도구가 있으면 담당 세션이 본 채팅으로 직접 보고한다. 없으면 담당 세션의 STATUS·영속 로그와 최종 응답에 같은 보고를 남기고, 본 세션은 사용자가 알려준 채팅 ID/MR을 조회해 취합한다. 자동 통지나 자동 후속 착수를 지원하지 않는 환경에서 이를 예약했다고 주장하지 않는다.
8. 현재 노출된 앱 도구에는 `create_thread`·`send_message_to_thread`가 없다. 부모는 인계 프롬프트를 준비했으며, 사용자가 2026-10-16 실제 M9 독립 채팅을 열었다. 현재 M9 thread는 `01a14026-e634-7fa3-b392-958f75b2b8e0`이다. 이 도구 제약은 실행 승인 부족과 다르다.
9. 사용자 최신 지시에 따라 워크플로의 에이전트 직접 main 병합 규칙 대신 사용자 MR 병합을 적용한다. 구현 세션은 단계 완료 시 다음 단계 인계 프롬프트를 남기되 후속 단계를 스스로 시작하지 않는다.

기존 최대 번호 M8 다음인 M9~M12를 할당했다. 2026-10-16 사용자 지시에 따라 각 마일스톤은 별도 독립 채팅에서 수행하며, 각 단계 내부의 독립 작업은 서브에이전트로 적극 병렬화한다. 단계 간 진행은 사용자 MR 병합 확인 후 순차적으로 한다. 이는 기존 M10/M11 준비 병행 제안보다 우선한다.

## M9. 기준 버전·운영 계약 확정

- 진행 목적: 릴리스와 판정에 사용할 한 기준을 만든다.
- AS-IS: 오래된 세션과 병합된 코드가 혼재한다.
- TO-BE: 기준 SHA·서비스 범위·품질 목표·운영 책임이 명시된다.
- 작업 종료조건: 두 조회 API가 있는 기준을 고정하고 범위·품질표·비밀 복구 설계를 검토 가능한 문서로 확정한다.

## M10. 실제 전화·조회 사용 흐름 완결

- 진행 배경: 현재 발신 성공 1회는 다중 턴이나 반복 신뢰성을 증명하지 않는다.
- 진행 목적: 전화 우선 기능의 사용자 결과를 검증한다.
- AS-IS: F02 일부·F03/F04 및 조회 실장이 남았다.
- TO-BE: 발착신·종료·조회·점유·오류 결과가 동일 후보에서 확인된다.
- 작업 종료조건: 필수 전화/조회 시나리오가 통과하고 BUG-003의 원인 또는 재현되지 않는 조건·잔여 위험을 명시적으로 판정한다.

- AS-IS: 착신 2턴 성공은 있으나 발신 2턴과 DTMF가 없다.
- TO-BE: F01~F03·필요한 D01~D03을 실행하고 종료 지연을 계측한다.
- 작업 종료조건: 실제 두 방향에서 최소 2턴·문맥·DTMF·상대 종료·회선 회수 증거가 있다.

#### M10-S1-T2. 발착신 연속 대화·종료 계측

- 진행 배경: 음성 두 턴과 시간 수치가 미완료다.
- 진행 목적: F02/F03 사용자 결과를 완결한다.
- AS-IS: 실발신 음성 미검증, 종료 버튼 시각 미수집이다.
- TO-BE: 허용 발신·착신 각각 같은 통화 2턴 이상, DTMF 수신, 사용자 종료 시각과 BYE/Idle을 함께 기록한다.
- 작업 종료조건: 두 방향의 청취·문맥·종료·다음 통화 수락 통과. DTMF는 별도 판정하며 실패를 통화 성공에 묻지 않는다. 미수신 반복 시 자동 재발신 없이 BUG-003 재현 증거를 남긴다.

- 작업 종료조건: 실제 기록·인증·부분 데이터·회선/세션 회수의 통과 증거가 있다.

#### M10-S2-T1. Caller ID·착신 목록·대화 조회

- 진행 배경: 번호 헤더 설정 오류는 번호 누락/오인으로 이어질 수 있다.

#### M10-S2-T2. 점유 충돌·중단·부분 기록

- 진행 배경: 정상 통화만으로 운영 실패를 판단할 수 없다.

- 작업 종료조건: 활성 세션 최대 1개, 미인증/원격 조회 거부, 무발화·부분 턴·종료 누락 의미 확인. Caller ID 변형은 합성과 현장 증거를 구분한다. 실장 불가 변형은 미확인으로 남겨 인수 때 예외 판정한다.

## A. 내부 의존성

## B. 외부 의존성

현장 담당자의 HT813 설정/FXO 상태 확인, 발화·수신 가능한 시험 시간, GPU/관측 VM 읽기·배포 권한, 기존 보존 키의 관리자가 필요하다. 비밀값·실제 번호를 문서나 채팅으로 수집하지 않는다. 테스트 대상과 운영 값은 추적되지 않는 설정으로 관리한다. RAM 증설·회선 변경은 측정 결과에 따라 별도로 결정한다.

# 6. 검증 전략

## A. 단위 테스트 (tests/units/)

릴리스 후보의 orchestrator/model-serving 기존 시험을 재실행하고 새 변경의 계약·취소·준비 상태·키 누락·보존 실패·조회 정렬/인증 회귀를 추가한다. 결함은 재현 실패→수정 후 통과 증거를 남긴다. 시험은 각 컴포넌트 README의 pytest 설정을 사용하고 가짜 피어/모델/API로 분리한다. PR의 122건을 새 버전의 통과 수로 재사용하지 않는다.

## B. 통합 테스트 (tests/integrations/)

- 통합 테스트 필요 여부 검토 결과: **필요**. 전화↔RTP↔모델/API↔암호화 파일↔조회 및 배포/재부팅은 단위 시험으로 대체할 수 없다.
- 사전승인 (Gate 1): **승인**. 2026-10-16 사용자 “네, 승인합니다”로 본 계획의 전화/조회·성능·복구·제한 운영 묶음 사전승인을 받았다. 단계 착수·완료 인수는 별도 MR 병합 게이트를 따른다. 기존 다른 계획의 승인을 재사용한 것이 아니다.
- 실행 직전 승인 (Gate 2): **로컬 격리 묶음 승인(A9), 실제 환경 묶음 미승인**. 명령·시간·전화 수·키/파일 경계·장비 영향·원복안을 담당 세션의 실행안 MR에 명시하고 통합 테스트 생성·실행 직전 담당 채팅에서 명시 응답으로 해당 묶음을 승인받는다. 준비용 MR 병합은 선행조건이 아니다. 결과 MR로 사후 소급 승인하지 않는다. 단계 완료 MR 병합만으로 내용 없는 후속 실전화·배포를 포괄 승인한 것으로 보지 않는다. 이미 받은 명시 응답이 정확히 해당 실행 묶음을 승인하고 조건이 유지되면 같은 승인을 다시 요청하지 않는다. FXO Idle·수신 준비 같은 현장 사실 확인은 별도로 수행한다.

# 7. 롤아웃 / 마이그레이션

1. 안전화 원격 최신 커밋을 기준으로 후보를 고정하고 새 문서·단위 회귀 및 필요한 합성 경계를 검증한다. 기존 로컬 이력/비밀은 공개하지 않는다.
2. 운영 중 전화 없음·FXO Idle을 확인한 점검 시간에 설정과 데이터 경로·동일 암호화 키 참조를 보존한다. 키 값을 릴리스 패키지에 넣지 않는다. 새 calls 경로·Caller ID 환경변수 매핑도 확인한다.
3. 모델 캐시·이미지·비밀 주입 준비 후 STT→TTS→backend 순으로 기동한다. 단일 worker와 포트 충돌·관리망 제한을 확인한다.
4. M10 실전화와 M11 성능/복구를 후보 버전에서 수행한다. 패키지나 앱이 바뀌면 영향받는 통화·조회 경계를 다시 확인한 후 M12에 진입한다.
5. 개시 차단 실패가 생기면 새 시험/발신을 중단하고 활성 통화를 정상 BYE로 정리해 FXO Idle을 확인한다. 이전 검증 이미지·설정을 복원하고 같은 키·데이터를 유지한다. DB 마이그레이션은 없지만 새 메타데이터와 구버전 삭제기의 호환성·고아 파일을 검증한다.
6. 이전 버전도 안전하게 통화할 수 없으면 서비스 중단을 유지하고 운영자에게 알린다. 검증되지 않은 FXS 자동 전환을 켜지 않는다. 데이터 볼륨 삭제·기존 키 교체는 롤백 수단으로 사용하지 않는다.
7. 72시간 제한 운영 후 사용자와 개시 여부를 판정하고 릴리스 버전/패치노트를 확정한다. 현재 dev/v0.0.1과 PRD/SRS 0.1.0의 버전명 차이도 M9에서 정리한다.

운영 시간은 M12 전, 장애 연락망·대체자·상시 백업 매체/접근자는 M11 적용 전에 확정한다. M10 현장 참여자 정보는 수집하지 않는다. 실제 번호·키·토큰·대화 원문을 채팅으로 요청하지 않는다.

다음은 **승인 전 상한 후보**다. SIP 재전송은 별도 통화가 아니지만 새 발신 시도·진단·재시도는 모두 집계한다.

|사례|방향(에이전트 기준)|최대 시도|조건|
|---|---|---:|---|
|D02|FXS→PSTN 진단 발신|0|현재 FXS 사용 불가. A9에서 이번 생략 예외 인수; D03 실발신 응답은 별도|

|F03|외부→에이전트 착신|1|2턴·문맥·DTMF·종료 시각·내역|
|F04-A/B|외부→에이전트 착신|2|A: 웹 점유 중 busy, B: 회수 뒤 착신 및 새 웹 busy, B 통화는 재생 중 상대 종료|
|F05|외부→에이전트 착신|1|조건부 표시 변형·음성 확인. 불가하면 미실행|

통화별 최대 점유 후보는 D02 0분, D03/F02 4분, F03 4분, F04-A 1분/F04-B 3분, F05 2분, 중단-P 2분, 취소-C 2분이다(합계 최대 18분, 나머지 12분은 확인·회수). 한도 도달 전에 담당자가 정상 종료하며 미완료 사례를 PASS로 바꾸지 않는다. 발신 직전 응답을 기다리는 동안에도 30분 창은 늘어나지 않는다.

총 최대 7시도 = 에이전트 발신 2 + FXS 진단 발신 0 + 착신 5. F05 불가 시 6. F04 busy 시도도 착신 수에 포함한다. 기존 계약의 F02 1/F03 1/F04 2/F05 조건부 1에 처리 중 종료·운영 취소 각 1회를 추가 제안한 것이며 포괄 승인이 아니다. 무발화/손상/종료 누락은 격리 합성 경계에서 우선 검증해 실회선 통화를 추가하지 않는다. 실제 무발화가 발생하면 별도 관측하되 계획된 2턴 성공을 대체하지 않는다.

매 발신 직전 이 담당 채팅에서 `사례 ID·대상 별칭·1회·최대 점유·FXO Idle/수신 준비·실행안 MR`을 제시해 요청하고 명시 응답을 기다린다. 응답 없는 대기에는 발신하지 않는다. 요청/응답의 KST 시각과 메시지 식별자(제공되지 않으면 시각과 요지), 해당 시도 ID만 로그에 남긴다. 원문 전체/번호는 남기지 않는다. 준비가 바뀌거나 해당 시도가 끝나면 응답을 재사용하지 않는다. FXS 현장 발신도 동일하다. 착신도 현장 담당자와 지금 걸 시점을 맞춘다.

## A3. 소스·실제 배포 차이 및 P0 확인 순서

최초 문서 후보는 M9 병합과 같았다. 재개 후 BUG-009의 착신 종료 대기 수정과 회귀시험을 이 브랜치에 누적하며, 실제 시험 후보 SHA는 수정 검증 후 고정한다. `080f5d3..f1c2088`의 앱 실행 코드·배포·스크립트·시험 코드는 동일하고 README·요구·운영/시험 기록만 변경됐다. 이것이 **실제 배포가 후보와 같다**는 증거는 아니다.

|비교 대상|관측 결과|허용 변경 / 차단|

|STT/TTS 이미지·실제 준비|둘 다 running/healthy, /ready HTTP 200. immutable 이미지 ID는 log-06|M10에서 모델 교체·재빌드·캐시 삭제 없음. 현재 모델이 호환·ready가 아니면 중단 후 범위 재검토|

이전 채팅에서 접속 경로를 찾아 SSH·컨테이너 상태·모델 준비·파일 수를 읽기 확인했다([log-06](../2_logs/VOIC-OPS-008-log-06.md)). 아래는 시험 직전 반복할 확인 목록이다. 실제 배포는 Git checkout이 아니므로 R1은 새 후보 checkout에서만 수행하고, 부재 backend의 inspect 실패를 무시한 채 배포하지 않는다. `$M10_DEPLOY_DIR`, `$M10_ENV_FILE` 등은 비공개 경로 참조다. 환경 파일을 `source`하거나 출력하지 않는다. `docker inspect` 전체/`docker compose config` 전체/`ps e`/패킷 원문/pcap/오디오 캡처는 공유하지 않는다.

```sh
# R1: 확인된 운영 checkout에서 소스와 상태만
cd "$M10_DEPLOY_DIR"
git rev-parse HEAD
git status --porcelain
# R2: 환경·마운트 내용을 출력하지 않는 컨테이너 식별
sudo -n docker compose --env-file "$M10_ENV_FILE" -f deploy/gpu/compose.yaml -f deploy/gpu/compose.backend.yaml ps -a --format json
sudo -n docker inspect --format '{{.Image}} {{.State.Status}}' "$M10_BACKEND_CONTAINER"
sudo -n docker image inspect --format '{{.Id}} {{json .RepoDigests}} {{index .Config.Labels "org.opencontainers.image.revision"}}' "$M10_BACKEND_IMAGE"
# R3: 준비 확인 — 상태 코드와 health 상태 필드만 허용
curl --silent --show-error --max-time 3 --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:8101/ready
curl --silent --show-error --max-time 3 --output /dev/null --write-out '%{http_code}\n' http://127.0.0.1:8102/ready
curl --silent --show-error --max-time 5 http://127.0.0.1:8000/health
free -m
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv,noheader
ss -lun
```

컨테이너 식별자는 운영 이름을 포함할 수 있으므로 공개 로그에는 역할 별칭·상태·SHA만 옮긴다.

P0는 backend 부재 상태에서 다음 네 단계로 나눈다.

1. **P0-A 배포 전:** 기존 키/데이터 경로·보호 사본/복원 가능성, 후보 소스/이미지/설정, 모델 ready·자원, 기존 backend 부재와 API/SIP/RTP 포트 가용성, D01 장비 설정·Caller ID 헤더 및 FXO Idle을 확인한다. 아직 없는 backend의 ready·인증 성공을 요구하지 않는다.
2. **후보 backend 기동:** 실제 환경 통합 Gate 2 명시 승인과 P0-A 충족 후에만 A4의 단일 backend를 생성한다. STT/TTS/관측을 재생성하지 않는다.
3. **P0-B 기동 후:** 단일 worker·loopback API·보존 ready·같은 경로/키·인증 경계·관측기·30분 종료 타이머, SIP/RTP 바인딩, F01의 기능 코드/비허용 번호 거부와 INVITE 0을 확인한다. 실패하면 신규 통화 없이 정상 종료하고 backend 부재로 회수한다.
4. **실전화:** P0-B 통과 후 매 실제 발신 직전 현재 FXO Idle·수신 가능 여부와 1회 응답을 확인한다. 착신도 준비 신호 후 요청한다. 7시도는 상한이며 완료조건이 아니다. 발착신 다중 턴·DTMF·정상/처리/재생 종료·회수·실제 내역·충돌·취소·다음 전화 수락을 항목별 판정한다. 미검증은 사유/필요 입력을 남기고 추가 통화가 필요하면 별도 범위/상한과 직전 발신 응답을 받는다.


## A4. 최소 시험 배포와 원복 명령

현재 관측한 원복 기준은 backend 부재다. A7 보호 사본·암호문 인증 및 P0-A가 충족되기 전에는 배포하지 않는다. P0-B는 후보 기동 후 수행한다. 모델/관측은 현행 서비스를 사용하고 backend만 후보 이미지로 일시 교체한다. 기존 backend가 없으면 ‘부재 상태’ 자체가 원복 기준이다. 현재 프로세스가 Compose 관리인지 확인되지 않으면 아래 명령을 적용하지 않는다. 다른 배포 방식은 구체 명령·영향·원복을 보완해 담당 채팅에서 확정한다.

변경 후보는 backend 이미지, `VOICE_AGENT_HT813_INBOUND_ENABLED`, 실제 장비와 일치하는 `VOICE_AGENT_HT813_CALLER_ID_HEADER`, 정확 허용 목록, 기존 데이터/비밀 경로 전달 및 시험용 메타데이터 관측 진입점이다. **포트·Dial Plan·종료 톤·인증·방화벽 변경은 현재 제안에 없음**. 필요하면 차이와 원복을 먼저 제시한다. Compose에 매핑되지 않는 값을 `.env`만 바꿔 적용했다고 하지 않는다.

운영 기동은 실제 환경 Gate 2 이후다. 시험 overlay [compose.m10.yaml](../../../deploy/gpu/compose.m10.yaml)은 `backend.image=voice-agent-backend:m10-<고정SHA>`, `restart: "no"`, 단일 worker의 시험 진입점, 기존과 같은 데이터·비밀 마운트를 지정한다. 관측 코드는 아래 A6 범위의 wrapper이며 제품 API/데이터/전화 정책을 변경하지 않는다. 후보 코드·관측 코드의 실제 SHA/이미지 ID·overlay 해시는 생성 후 기록하고 소스 diff를 확인한다. 동작 변경이 필요하면 결함/계획 절차로 재검토한다.

```sh
# D1: 승인 후 별도 후보 checkout. 기존 운영 checkout/reset/clean 금지
# M10_TEST_SHA는 승인된 소스+범위 내 계측 코드의 실제 commit으로 고정한다.
cd "$M10_CANDIDATE_DIR"
test "$(git rev-parse HEAD)" = "$M10_TEST_SHA" || exit 1
test -z "$(git status --porcelain)" || exit 1
git merge-base --is-ancestor f1c208811fb0e04208e384242f674ebd670c8857 HEAD || exit 1
sudo -n docker build -f deploy/gpu/Dockerfile.backend -t "voice-agent-backend:m10-$M10_TEST_SHA" .
# overlay는 새 시험 harness 경로를 read-only로 마운트하고 진입점 변경; 키 값은 포함하지 않음
sudo -n docker compose --env-file "$M10_ENV_FILE" -f deploy/gpu/compose.yaml -f deploy/gpu/compose.backend.yaml -f "$M10_TEST_OVERLAY" config --quiet
# 활동 통화 0/FXO Idle, 복원 자료 확인 후에만 기존 backend 정상 중지
sudo -n docker compose --env-file "$M10_ENV_FILE" -f deploy/gpu/compose.yaml -f deploy/gpu/compose.backend.yaml stop -t 15 backend
# 실제 이미지와 overlay를 확인한 뒤 모델/관측 재생성 없이 backend만 생성
sudo -n docker compose --env-file "$M10_ENV_FILE" -f deploy/gpu/compose.yaml -f deploy/gpu/compose.backend.yaml -f "$M10_TEST_OVERLAY" up -d --no-deps --no-build backend
```

backend-only 빌드는 STT/TTS 이미지를 바꾸지 않는다. 기존 이미지 태그의 덮어쓰기/삭제/prune를 하지 않는다. M10 wrapper는 시작 후 30분에 정상 종료를 시작하며 재시작하지 않는다. 시작 직후 deadline을 KST로 기록하고 창 종료 5분 전부터 새 통화를 받지 않도록 현장과 조율한다. timeout은 시험 창 종료이며 정상 통화 중 무음 제한을 새로 도입하는 것이 아니다. 장비 전체 착신 정책을 임의 변경하지 않는다.

원복 overlay는 작업 전 확보한 **기존 immutable backend image ID·기존 명령·기존 restart 정책**만 지정하며 같은 데이터/비밀 경로를 유지한다. 시험 wrapper/mount는 원복 명령에 포함하지 않는다.

```sh
# D2: 먼저 발신은 API DELETE, 착신은 상대 종료 또는 backend SIGTERM으로 정상 BYE
# compose stop은 15초 뒤 SIGKILL 가능: 10초 안 정상 종료 관찰, 미회수면 실패·현장 회수 판단
sudo -n docker compose --env-file "$M10_ENV_FILE" -f deploy/gpu/compose.yaml -f deploy/gpu/compose.backend.yaml -f "$M10_TEST_OVERLAY" stop -t 15 backend
# FXO Idle·RTP 해제 확인 뒤 기존 검증 설정으로 돌아감
sudo -n docker compose --env-file "$M10_ORIGINAL_ENV_FILE" -f "$M10_ORIGINAL_COMPOSE" -f "$M10_ORIGINAL_BACKEND_COMPOSE" -f "$M10_ROLLBACK_OVERLAY" config --quiet
sudo -n docker compose --env-file "$M10_ORIGINAL_ENV_FILE" -f "$M10_ORIGINAL_COMPOSE" -f "$M10_ORIGINAL_BACKEND_COMPOSE" -f "$M10_ROLLBACK_OVERLAY" up -d --no-deps --no-build backend
```

현재 확인한 backend 부재가 유지되면 위 원래 서비스 복원 up은 실행하지 않고 아래 부재 분기를 적용한다. 실행 직전 상태가 바뀌면 재평가한다. 원래 backend가 실행 중일 때만 위 마지막 up을 실행한다. **원래 중지였으면** 같은 원복 명령을 `up --no-deps --no-build --no-start backend`로 실행해 원래 이미지/명령/mount/restart 설정의 미기동 컨테이너를 복원한다. **원래 부재였으면** 시험 backend가 중지됨과 `/data`·비밀의 외부 마운트를 확인하고 시험 Compose 조합에서 `rm -f backend`로 시험 컨테이너만 제거한다(`-v` 금지). 시험 wrapper 컨테이너를 남겨 이후 start에서 다시 실행되게 하지 않는다. [Docker up의 --no-start](https://docs.docker.com/reference/cli/docker/compose/up/)와 [rm의 볼륨 보존](https://docs.docker.com/reference/cli/docker/compose/rm/)을 기준으로 하며 현장 Compose 버전의 옵션 지원도 읽기 확인한다. 원래 이미지/설정이 안전하게 실행 가능한지 확인되지 않으면 복구됐다고 선언하지 않는다. 회선이 남으면 신규 통화 없이 김화균에게 현장 회수를 요청한다. 데이터/모델/관측 volume 삭제, 키 교체, `down -v`, VM 재부팅, 미검증 FXS 자동 우회는 원복 수단이 아니다.

## A7. 보존·중지·완료와 증거

작업 전 기존 설정의 제한된 사본과 원복 명령을 준비하고, 키 관리자가 정본 키의 복구 가능성을 내용 비출력으로 확인한다. 기존 데이터 경로/마운트·권한/파일 수와 실제 기존 암호문 1건의 같은 키 인증 가능성을 보호된 환경에서 확인한다. API 원문을 공유하는 대신 복호화/무결성 성공 여부만 기록한다. 새 빈 경로의 ready는 동일 키 검증이 아니다. 암호문 백업이 필요하면 별도 보호된 경로에 완성 파일만 복사하며 생성시각+30일 만료를 유지한다. M10 작업 전 보호 사본은 동일 GPU의 별도 비공개 디렉터리(0700, 파일 0600)에 기존 암호문·메타데이터·설정만 보존하고 파일 수·SHA manifest를 대조한다. 기존 소유 계정의 권한을 유지하며 현장 참여자 정보를 수집하지 않는다. 디스크 장애용 독립 백업을 검증했다고 주장하지 않는다. 시험 중 기존 자료가 변경/삭제되면 신규 시험 자료를 별도로 보존한 뒤 보호 사본의 해당 파일만 원래 경로/권한으로 복원한다. 키 정본은 기존 로컬 0600 설정에 유지한다. 작업용 tmpfs 주입은 Gate 2 후 기존 키를 사용하며 내용 비출력·권한 확인 후에만 backend에 연결한다. 보호 사본 또는 키 인증이 실패하면 배포 전 차단한다. 상시 백업 시스템을 이 단계에서 도입하지 않는다.

**암호문 인증의 명시적 승인 대상:** 원격 기존 대화 암호문 1건(1 MiB 미만)을 인증된 SSH로 이 작업 환경의 프로세스 메모리에 전송하고, 기존 로컬 키로 AES-GCM 인증·JSON 형식 확인 후 폐기한다. 평문/키를 디스크·도구 출력·Git에 남기지 않으며 성공 boolean만 기록한다. 최초 읽기 시도는 자동 승인 검토가 명시적 승인 부재로 거절했다. 이후 A9에서 이 1건을 명시 승인받았고 log-08에 실제 검증 결과를 기록한다. 다른 파일·범위에 재사용하지 않는다. 관리 정정이나 MR 병합을 포괄 승인으로 해석하지 않는다.
