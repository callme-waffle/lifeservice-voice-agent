# 1. 배경 및 맥락

[ADR-004](ADR-004-ht813-direct-outbound-telephony.md)는 처음에는 HT813 FXO를 통한 에이전트 외부 발신만 전화 채널에 넣고, 외부 착신은 향후 FXS 전화기에 전달하도록 정했다. 사용자는 2026-09-24 M6 대화에서 발신자 Caller ID별 에이전트/FXS 분기를 검토한 뒤 **모든 외부 착신을 발신자 번호와 관계없이 에이전트에 연결**하도록 정정했다. 기존 에이전트 외부 발신의 정확한 목적지 허용 번호 정책은 유지한다. FXS 전화기는 아직 연결되지 않았고 이번 Phase의 FXS 실장 검증은 승인되지 않았다.

제조사 [HT813 관리 가이드](https://documentation.grandstream.com/knowledge-base/ht813-administration-guide/)는 PSTN 착신 전체를 지정 SIP 대상에 전달하는 `Unconditional Call Forward to VoIP`와 전체 착신의 FXS 링스루 설정, PSTN Caller ID의 SIP 전달을 설명한다. [HT813 직접 피어링 가이드](https://documentation.grandstream.com/knowledge-base/peering-ht8xx-with-ht813/)는 별도 SIP 서버 없이 VoIP 피어에 PSTN 착신을 전달하는 구성을 제시한다. 이는 제품 기능의 문서 근거이며 현재 장비의 인증·코덱·RTP·번호 전달·종료 신호와 앱 상호 운용성은 확인되지 않았다.

현재 앱의 `UDPSIPPeer`는 발신 응답만 받는 최소 SIP 클라이언트이고 `HT813Outbound`는 발신 전용이다. 같은 UDP 주소/포트의 착신 INVITE와 발신 응답을 안전하게 나누는 수명 관리가 없다. 외부 착신을 받으려면 SIP 수신 경계, SDP 응답, RTP 수명, 전화 세션 점유 및 원격 종료를 구현해야 한다.

---

# 2. 검토한 대안

## A. HT813가 모든 FXO 착신을 앱의 직접 SIP 피어로 보내고 앱이 수신

- 장점: 기존 FastAPI 단일 컴포넌트와 직접 SIP/RTP 방향을 유지하며 별도 PBX를 설치하지 않는다. 발신과 착신에서 공통 다중 턴·모델 코어를 사용할 수 있다.
- 단점: 앱이 SIP UAS·피어 검증·동시 대화·착신 실패 응답과 발신/착신 소켓 공존을 책임진다. 실제 HT813와의 상호 운용성이 미검증이다.

## B. 별도 SIP PBX를 착신 라우터로 두고 에이전트와 HT813를 등록

- 장점: SIP 등록·라우팅·재시도·회선 상태 관리에 성숙한 기능을 사용할 수 있다.
- 단점: 현재 없는 서버와 서비스 배포·운영이 추가된다. Caller ID별 분기가 사라진 현재 요구에는 라우터의 복잡성이 꼭 필요하지 않다.

## C. FXS를 먼저 울리고 미응답 통화만 에이전트로 전달

- 장점: HT813의 기존 링스루와 지연 전달 설정을 활용할 수 있다.
- 단점: 사용자가 정정한 모든 착신의 에이전트 직접 접근을 만족하지 않는다. FXS 단말도 아직 없다.

---

# 3. 결정

**대안 A를 채택한다.** HT813 FXO에 들어온 PSTN 착신을 앱의 SIP 수신 주소로 모두 전달하고, 발신자 Caller ID 값·누락 여부로 에이전트 접근을 제한하지 않는다. 기존 외부 착신→FXS 링스루는 M6의 활성 착신 경로에서 제외한다. 장비의 구체 설정 전/후 값과 적용·복구 절차는 읽기 전용 현황 확인 및 백업 뒤 Gate 2에서 확정한다. FXS 전화기의 외부 발신 요구는 남기되 전화기 연결 전에는 실장 완료로 판정하지 않는다.

앱은 설정된 HT813 피어 주소에서 온 SIP 착신만 수락하고, Caller ID는 인증 수단으로 사용하지 않는다. 잘못된 SIP/SDP·타 출처 요청은 모델·작업 API 호출 전에 거부한다. 다른 웹/전화 세션이 사용 중이면 새 착신에 명시적 통화 불가 응답을 보내고 기존 통화는 유지한다. 수락한 착신은 발신 통화와 같은 한 통화의 다중 턴·상대방 종료·문맥 전송 원칙을 적용한다. 전화 코어는 발신/착신을 합쳐 전역 단일 세션을 점유하고 RTP·DTMF·음성 출력 순서를 유지한다.

기존 **에이전트 외부 발신 목적지 허용 번호 제한**은 유지한다. 발신 요청은 허용 목록이 비어 있으면 생성되지 않고 허용되지 않은 목적지로 SIP 패킷을 보내지 않는다. 착신의 Caller ID 무제한과 발신 목적지 무제한은 서로 다른 정책이다.

이 ADR은 사용자 요구 자체가 아니라 그 구현 경계의 선택이다. 사용자는 2026-09-24 M6 대화에서 **구현 가능 조건으로 진행**을 승인했다. 제조사 자료상 전체 착신의 VoIP 전달 경로가 있으므로 이 방식을 우선 구현·검증한다. 실제 HT813 상호 운용성에 실패하면 6절의 재검토 조건에 따라 계획·아키텍처를 다시 검토한다. M6 계획 변경은 별도 사용자 승인으로 반영한다.

---

# 4. 결정 사유

번호별 분기가 사라져 SIP PBX의 라우팅 기능 없이도 HT813의 전체 PSTN→VoIP 전달과 앱의 SIP 수신 경계로 요구를 구현할 수 있는 후보가 생겼다. 단일 에이전트 컴포넌트와 기존 HT813 직접 발신 방향을 유지하면 배포 구성 요소가 늘지 않는다. 다만 제조사 설정 예가 현 장비·현재 네트워크의 통화 성공을 보장하지 않으므로 승인된 실장 검증이 필수다.

---

# 5. 결과 및 영향

## A. 쉬워지는 것

- 발신자 번호 표시 여부와 관계없이 같은 에이전트 대화 경로를 제공할 수 있다.
- 번호별 FXS/에이전트 분기 정책과 외부 PBX 서비스가 필요하지 않다.

## B. 어려워지거나 제약되는 것

- SIP 수신, 피어 인증/검증, SDP·RTP, 원격 BYE, 동시 세션 busy와 발신/착신 소켓 수명 관리가 M6에 추가된다.
- 외부 회선의 모든 착신이 에이전트/API 자원을 사용할 수 있으므로 전역 단일 세션, 처리 시간 제한, 회선 회수·장애 관찰이 필요하다.
- 앱이 응답하지 않거나 전화 회선이 점유된 경우 통화가 에이전트에 도달하지 못할 수 있다. FXS 자동 우회 성공은 이 결정에 포함하지 않는다.
- FXS 전화기 미연결 상태에서 FXS 외부 발신·회선 충돌은 검증할 수 없다.
- HT813 설정 변경·실착신·통합 테스트는 새 시나리오 Gate 1과 실행 직전 Gate 2, 설정 백업·복구 절차가 있어야 한다.

---

# 6. 재검토 조건

- HT813의 전체 PSTN→VoIP 전달 또는 앱 직접 SIP 수신이 실장 시험에서 작동하지 않는 경우
- 사용자가 FXS/에이전트 번호별 분기, 여러 착신 동시 처리, 콜백·전환·통화 대기, 앱 장애 시 FXS 우회를 요구하는 경우
- 현재 네트워크가 HT813에서 앱의 SIP/RTP 주소에 도달할 수 없고 배포 토폴로지 변경이 필요한 경우
