# 1. 배경 및 맥락

M5-S4 웹 음성 채널 구현 전에 SRS-W01~W03의 미확정 브라우저 전송·접근 규격을 정해야 한다. 내부 오디오는 16 kHz 모노 PCM16이고 세션·이벤트에는 UUID와 순서 번호가 있다.

---

# 2. 검토한 대안

## A. HTTP 요청마다 오디오 청크 전송

- 장점: 단순한 요청 단위 인증과 처리.
- 단점: 양방향 음성·이벤트와 취소·역압의 수명 주기를 여러 요청에 걸쳐 조정해야 한다.

## B. WebSocket으로 오디오와 이벤트 교환, 연결 전 런타임 토큰 인증

- 장점: 한 연결에 세션의 양방향 데이터와 종료·취소 이벤트를 묶을 수 있다.
- 단점: 연결 수명 주기, 인증 헤더, 오디오 프레임과 JSON 이벤트의 순서·역압을 명시해야 한다.

---

# 3. 결정 내용

사용자가 대안 B를 선택했다. 웹 채널은 WebSocket으로 16 kHz 모노 PCM 청크와 JSON 이벤트를 교환한다. 연결 수락 전에 런타임 설정의 토큰으로 접근 권한을 확인한다. 브라우저가 임의의 `Authorization` 헤더를 지정하기 어려워 M5에서는 `Sec-WebSocket-Protocol`에 `voice-agent`와 `token.<토큰>`을 요청하고 응답에는 `voice-agent`만 보낸다. 토큰은 응답·애플리케이션 로그에 포함하지 않는다. 이진 프레임은 4바이트 순서 번호와 PCM 데이터이며 세션 UUID는 연결 시작 응답으로 발급된다. 세션·순서·취소·오류 의미는 M4 공통 계약을 따른다.

---

# 4. 결정 사유

한 세션의 음성 입력·출력과 상태 이벤트를 하나의 연결 수명 주기로 다루는 편이 공통 계약의 종료·취소 의미에 맞다. 연결 전 인증은 권한 없는 요청이 모델·작업 처리로 전달되기 전에 차단한다.

---

# 5. 결과 및 영향

## A. 쉬워지는 것

웹 세션의 데이터 순서, 연결 해제와 취소를 한 채널에서 관리한다.

## B. 어려워지거나 제약되는 것

브라우저가 토큰을 안전하게 전달하는 배포 방식과 WebSocket 프레임 스키마를 명시해야 한다. 실제 브라우저·서비스 경계는 M6의 승인된 통합 검증 전까지 미검증이다.

---

# 6. 재검토 조건

브라우저 인증 제약으로 연결 전 토큰 전달이 불가능하거나 WebSocket이 목표 전송 환경에서 제한되면 재검토한다.
