# 1. 배경 및 맥락

work-vm `198.51.100.67`의 `/workspace/voice-agent`에서 개발 중이다. 기존 통합 시험은 GPU `198.51.100.74`로 코드를 복사하고 이미 준비된 Python 3.11 모델 환경에서 앱 전체를 실행했다. 코어가 원격 GPU API를 호출하는 구조가 아니라 STT/TTS를 같은 프로세스에서 직접 로드한다.

사용자가 참조한 ChatGPT 대화에는 Ubuntu 라우터의 `ens19=192.0.2.4/24`, `ens21=198.51.100.1/24`와 `198.51.100.0/24 → ens19 MASQUERADE`가 전사돼 있다. 원본 첨부 이미지는 read_thread에 포함되지 않았으므로 이를 직접 확인한 설정이라고 표현하지 않는다. 이 구조라면 과거 HT813가 관측한 출발지 `.4`를 설명할 수 있다. FORWARD 기본 정책 ACCEPT만으로 규칙 전체의 통과를 증명할 수 없고, DNAT 부재도 목적지를 직접 GPU로 지정한 시험의 실패 원인을 단독 증명하지 않는다.

현재 재조회에서 GPU SSH는 `No route to host`, work-vm의 해당 이웃 상태는 FAILED였다. VM 전원·주소 변경·브리지·방화벽 중 원인을 단정하지 않는다. GPU의 현재 실행 환경은 확인하지 못했다.

---

# 2. 검토한 대안

## A. GPU VM에 HT813 LAN용 NIC 추가

- 장점: 기존 관리망과 단일 앱 구조를 유지하면서 전화 트래픽에서 NAT를 제거할 수 있다. 현재 코드의 단일 바인딩/광고 주소 구조와 맞는다.
- 단점: HT813 LAN에 실제 연결된 Proxmox 브리지/물리 포트 또는 VLAN이 필요하며, 두 망에 연결된 서버의 접근 통제와 경로 확인이 필요하다.

## B. 기존 두 대역 사이의 라우팅 및 선택적 NAT 예외 구성

- 장점: GPU에 NIC를 추가하지 않고 원본 주소를 유지할 수 있다.
- 단점: HT813 측 다음 홉/정적 경로, 라우터 FORWARD 규칙과 NAT 예외의 양방향 정합 확인이 필요하다.

## C. SIP/RTP 포트 전달 및 광고 주소 분리

- 장점: 기존 NAT 배치를 유지할 수 있다.
- 단점: 현 앱은 바인딩과 SIP/SDP 광고 주소가 같은 값이다. 별도 주소 지원·피어 검증·SIP/RTP 매핑 검증이 추가될 수 있어 우선순위가 낮다.

## D. CPU 서버의 전화 코어와 GPU 추론 서비스를 분리

- 장점: 장기적으로 각 서버의 배치·확장을 독립시킬 수 있다.
- 단점: 현재 원격 추론 어댑터가 없으며 새로운 인터페이스·서비스·장애 경계 구현이 필요하다. 이번 연결 문제 해결 범위에서는 우선하지 않는다.

---

# 3. 결정 내용

**대안 A를 제안했다. 이후 사용자가 LAN NIC와 .23 주소 및 DHCP 경로/DNS 보완을 적용했고, 2026-10-06 GPU 전체 앱의 30분 착신 시험 실행을 명시 승인했다.** work-vm은 개발·테스트·배포 제어용으로 유지하고 GPU VM에는 FastAPI·STT/TTS·웹·SIP/RTP·보존을 포함한 전체 앱을 설치한다.

- 기존 관리 NIC의 `198.51.100.74`와 기본 경로를 유지하는 것을 목표로 하되 현재 VM 상태부터 재확인한다.
- 추가 NIC를 HT813의 실제 LAN/VLAN에 연결된 브리지에 붙인다. GPU의 새 `192.0.2.x/24`는 사용 가능 여부와 DHCP 예약/충돌 확인 후 확정한다. 대화의 `.50`은 예시다.
- 추가 NIC에 두 번째 기본 경로를 넣지 않는다. DHCP 사용 시 기본 경로와 DNS 유입 정책을 명시한다.
- `VOICE_AGENT_HT813_LOCAL_IPV4`를 새 LAN IP로 지정한다. 현재 코드는 발신/착신 SIP 바인딩, RTP 바인딩, SIP Contact/Via 및 SDP에 이 주소를 사용한다. HTTP 바인딩은 별도 `VOICE_AGENT_API_HOST`다.
- 앱의 현재 기본 UDP 포트는 발신 SIP/RTP `5060/4000`, 착신 `5061/4002`다. 넓은 RTP 범위를 추정해 개방하지 않는다. HT813와의 실제 협상 포트를 함께 검증한다.
- GPU VM이 두 망을 중계하지 않도록 하고 전화 NIC에는 필요한 HT813 트래픽만 허용한다. 운영 API는 기존 loopback 제약을 유지한다.

---

# 4. 결정 사유

앱 전체를 별도 GPU 서버에서 실행한 선행 증거가 있고, 현재 STT/TTS는 CUDA를 직접 사용한다. 실행 서버만 같은 LAN에 연결하면 기존 단일 프로세스 구조를 유지하면서 전화 경로의 NAT·광고 주소 불일치 가능성을 줄일 수 있다. work-vm에만 LAN NIC를 추가해도 원격 GPU에 있는 전화 런타임의 경로는 해결되지 않는다.

# 5. 결과 및 영향

## A. 쉬워지는 것

전화 요청과 음성이 동일 LAN의 명시적 주소 사이를 흐른다. 개발 VM을 재시작해도 운영 프로세스가 계속 실행되는 배포 구성을 만들 수 있다. 주소 분리용 애플리케이션 변경 없이 검증할 수 있는 후보가 된다.

## B. 어려워지거나 제약되는 것

네트워크 변경만으로 HT813 코덱·번호 전달·원격 종료 호환성이 증명되지는 않는다. 기존 M6 실장 기준을 유지한다. 현재 deploy에는 .gitkeep만 있고 서비스 설치·배포·롤백이 없다. pyproject에는 모델 런타임 의존성이 포함되지 않았으며 시험 코드에는 원격 주소·경로가 고정돼 있다.

상시 서비스 설치·배포 선택은 아직 승인/실행하지 않았으므로 이 문서 전체의 상태는 proposed를 유지한다. 적용된 LAN과 승인된 단기 시험은 [log-41](../2_logs/VOIC-FEAT-001-log-41.md)·[log-42](../2_logs/VOIC-FEAT-001-log-42.md)·[log-43](../2_logs/VOIC-FEAT-001-log-43.md)에 구분한다.

운영 배포에는 검증한 Python 3.11/CUDA/모델 라이브러리·가중치 버전 고정, 설치 가능한 릴리스, 비밀 주입, 암호화 키와 보존 데이터의 지속 저장, 단일 작업자 서비스 관리, 배포/롤백·실통화 검증이 필요하다. 우선 기존 GPU VM의 가상환경과 systemd 서비스 구성을 제안하며 컨테이너화는 별도 선택으로 남긴다. 과거 약 4 GiB RAM 제약과 모델별 반복 로드를 고려해 메모리 여유를 늘리고 실제 턴 지연을 재측정할 필요가 있으나 구체 자원 증설량이나 상주 모델 변경은 확정하지 않는다.

---

# 6. 재검토 조건

- HT813 LAN에 연결 가능한 브리지/VLAN이 없거나 망 분리 정책이 추가 NIC를 허용하지 않는 경우
- 기존 GPU VM 복구가 불가하거나 다른 호스트가 더 적합한 경우
- 다중 서버 추론·동시 세션 확장이 요구되는 경우
- 같은 LAN에서도 실제 전화 상호 운용성이 실패하는 경우
