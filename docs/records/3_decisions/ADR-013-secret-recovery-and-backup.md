# 1. 배경 및 맥락

현재 backend Compose는 호스트의 `VOICE_AGENT_SECRETS_DIR` 아래 세 파일을 `/run/secrets`로 전달하며 앱은 `_FILE`로 읽는다. 원본 파일의 생성·부팅 후 복원은 구현하지 않는다. 과거 일시 시험은 tmpfs에 키를 넣고 종료 후 제거했다. restart 정책과 모델 health 의존만으로 호스트 재부팅 후 비밀·같은 키·시작 순서가 복구됐다고 판단할 수 없다.

기존 암호문 recordings/transcripts/calls는 같은 보존 키로 계속 읽어야 한다. 현재 설정 검증은 키의 Base64/32바이트 형식만 확인하므로 **형식이 맞는 다른 키가 기존 자료의 올바른 키인지 기동 시 보증하지 않는다**. 코드 변경과 운영 복구 검증은 M11 범위다. M9는 실제 키·운영 파일을 읽거나 이동하지 않았다.

ADR-008의 AES-GCM·30일·런타임 키 전달, ADR-012의 동일 보존 키와 calls 메타데이터, ADR-011의 STT/TTS/backend 배치를 유지한다. 호스트에서 키를 지속 보관하는 새 접근 경계는 이 제안의 명시적 리뷰 항목이다. 기존 결정의 수락 상태를 바꾸지 않는다.

# 2. 검토한 대안

|대안|복구시간·가용성|접근·보관 경계|장점|제약|
|---|---|---|---|---|
|A. 관리자 수동 tmpfs 재주입|담당자 응답 시간에 의존, ≤10분 보장 불가|김화균이 보유한 기존 비밀을 인증된 채널로 메모리에만 주입|호스트 재부팅 후 평문 원본이 남지 않음|무인 복구 불가. 선택하면 무인 상시 서비스 합격으로 판정하지 않음|
|B. 보호된 호스트 원본→부팅 tmpfs 주입|호스트만 정상이라면 무인 복원 설계 가능; 시간 실측 필요|GPU 호스트 root 전용 영속 원본, 제한된 부팅 로더·Docker 관리자|기존 `_FILE`·Compose 경계 재사용, 외부 저장소 장애에 의존하지 않음|호스트/root/Docker 또는 디스크 탈취 시 키 노출 가능. 단순 파일 권한은 디스크 암호화가 아님|
|C. 외부 비밀 저장소/부팅 주입|저장소·인증·네트워크 가용성 의존|별도 서비스와 부팅 신원·복구 자격 관리|중앙 통제·호스트 평문 원본 축소|현재 저장소·인증 인프라 근거 없음. 부팅 자격의 보관 문제와 새 의존성 추가|

# 3. 결정 내용

**권고안은 B이며 아직 선택·승인·구현되지 않았다.** 사용자가 M9 MR의 이 설계를 검토·병합한 뒤 승인 증거(merge SHA·병합자·시각)를 별도 기록하고 accepted로 추적한다. 운영 적용·비밀 전달·재부팅은 M11 구체 실행안의 Gate 2 범위에서만 수행한다. A를 선택하면 담당자 재주입 전 서비스 중단을 명시하고 무인 목표 미충족으로 처리한다. C를 선택하면 저장소·부팅 인증·가용성 설계를 다시 리뷰한다.

## A. 경로와 접근자 제안

아래 경로는 새 설계의 제안명이며 실제 존재·승인된 위치가 아니다. 실제 주소·번호·비밀값은 Git에 기록하지 않는다.

|대상|제안 위치|접근자·정책|
|---|---|---|
|세 비밀의 영속 원본|GPU 호스트 `/etc/voice-agent/secrets/`|root 소유 디렉터리 0700, 파일 0600; `task_api_key`, `web_access_token`, `data_encryption_key`|
|런타임 복사본|GPU 호스트 `/run/voice-agent/secrets/` tmpfs|부팅 로더만 생성·검증·원자 게시; 같은 모드, Compose의 `VOICE_AGENT_SECRETS_DIR` 연결|
|운영 데이터|기존 `VOICE_AGENT_DATA_DIR` 유지|recordings/transcripts/calls와 삭제 감사. 실제 경로는 관리자 비공개 설정 확인|
|호스트 손실 대비 키 사본|김화균 관리의 별도 암호화 오프라인 매체|데이터 백업과 분리. 매체 식별자·위치·복구 암호 접근자는 적용 전 비공개 운영 인수대장에 확정|
|암호문 데이터 백업|GPU와 다른 장애 영역의 별도 암호화 백업 매체|김화균 책임, root 백업 작업만 접근. 백업 대상·매체·용량은 적용 전 확정|

김화균을 비밀/복구 책임자로 제안하며 다른 관리자 접근은 자동 허용하지 않는다. 호스트 root와 Docker 권한자는 실행 중 비밀을 읽을 수 있으므로 실제 계정·접근자 범위를 김화균이 확인해야 한다. 키를 이미지·릴리스 패키지·일반 `.env` 출력·CLI 인자·로그에 넣지 않는다. 디스크 암호화/부팅 해제 방식을 가정하지 않으며, 요구된다면 무인 부팅과 함께 재검토한다.

## B. 동일 키와 부팅 순서

1. 구현 전 기존 보존 키의 관리자가 정본을 확인한다. 새 키 생성·기존 키 교체를 하지 않는다. 백업의 키 사본과 운영 원본의 일치는 값을 출력하지 않는 제한된 검사로 확인한다.
2. 부팅 로더는 원본의 존재·소유자·권한·symlink 여부·형식, 데이터 마운트를 확인한다. 누락·오류면 backend 시작을 차단하고 내용 없는 실패 코드만 남긴다.
3. 기존 파일에 쓰기 전에 동일 키 검증을 한다. 제안은 실제 대화 대신 독립된 비개인 합성 검증 아티팩트를 동일 키로 암호화해 보호된 제어 경로에 두고 AEAD 인증만 검사하는 것이다. 파일에는 개인 정보가 없고 키 값·원문을 출력하지 않는다. 초기 도입 때 실제 보존 파일 1건도 승인된 격리 복원에서 내용 비출력으로 확인해야 기존 데이터 연속성을 증명할 수 있다.
4. 검증 아티팩트는 녹취 백업과 분리된 제어 자료이며 기존 30일 통화 보존 기간을 연장하지 않는다. 오염·유실 시 키를 자동 생성하지 않고 수동 확인한다. 이 검증 방식과 검사기는 현재 미구현이다.
5. 검증된 비밀을 tmpfs에 원자 게시한 후 접근 제한·데이터 권한을 확인한다. 단일 부팅 조정자가 STT ready→30초→TTS 워밍업 ready→단일 worker backend 순서를 책임진다. Docker daemon 자동 restart가 조정자를 우회하지 않도록 M11에서 시작 정책/의존성을 함께 구현·검증한다.
6. `/health`·지표를 확인하고 기존 내역의 인증된 조회·신규 통화까지 검증한다. 매 실전화 발신은 김화균에게 직전 요청한다. 준비 확인만 통과했다면 전화 복구 완료로 보고하지 않는다.

## C. 백업·만료·복구 제안

- 1시간 간격의 암호문 증분 백업, **호스트 손실 시 RPO ≤1시간 목표**를 제안한다. 아직 운영 요구로 승인된 값이 아니며 M11 처리량·스케줄 실패·관측으로 검증한다. 재부팅은 기존 디스크가 정상인 경우 파일 손실 0을 목표로 하되 미완성 원자 기록은 보장하지 않는다.
- 백업은 완성된 암호문만 수집하고 임시 파일은 제외한다. 데이터 원본을 삭제하거나 백업을 운영 볼륨에 덮어쓰지 않는다. 백업 실패와 마지막 성공 시각을 관측한다.
- **백업 시각이 아니라 각 아티팩트의 인증된 생성 시각+30일**에 원본과 모든 백업 사본을 만료시킨다. 삭제 불가능한 장기 스냅샷에 통화 파일을 넣지 않는다. 오프라인 매체를 포함해 만료를 제때 수행할 수 없는 데이터 백업 방식은 채택하지 않는다. 오프라인 키 사본은 통화 데이터 자체를 포함하지 않는다.
- 복원은 서비스를 중지하고 기존 볼륨을 보존한 채 별도 복구 경로에 수행한다. 올바른 키·권한·무결성을 검사하고 만료 파일을 신규 조회 전에 제외·삭제한다. 만료 시각을 복원 시각으로 갱신하지 않는다. calls와 texts의 일부 누락은 `incomplete`/부분 턴으로 드러내며 없는 내용을 복원했다고 만들지 않는다.
- 기존 조회 성공, 삭제 감사/만료, 모델 준비, 새 전화 및 회선 회수가 확인된 뒤 경로를 전환한다. 실패하면 기존 검증 이미지·설정·같은 키·데이터로 되돌리거나 서비스 중단을 유지한다. 데이터 볼륨 삭제·새 키 생성·FXS 자동 우회는 원복 방법이 아니다.
- ≤10분은 재부팅 후 복구 목표다. 호스트 전체 손실·새 하드웨어 교체의 RTO는 미정이며 같은 목표를 보장하지 않는다. 발신 직전 요청 대기까지 실제 경과시간에 포함해 기록하고 기술 준비 시간과 구분한다.

# 4. 결정 사유

현재 단일 GPU 호스트와 기존 파일 비밀 인터페이스를 활용하면서 무인 복구를 검증할 수 있는 가장 작은 변경이 B다. A는 현 방식과 가깝지만 무인 목표에 맞지 않는다. C는 별도 인프라가 실제 제공될 때 운영 부담·부팅 신원을 다시 판단해야 한다. 이 권고는 영속 평문 비밀과 관리자 접근의 위험을 사용자가 수용한다는 뜻이 아니다.

# 5. 결과 및 영향

## A. 쉬워지는 것

같은 키·기존 데이터 경로를 유지한 부팅·복구와 실패 시 시작 차단을 반복 검증할 수 있다. 서비스 데이터 백업과 키 손실 복구 책임을 구분한다.

## B. 어려워지거나 제약되는 것

비밀 원본 권한·호스트 보안, 부팅 조정과 Docker restart 충돌, 같은 키 검증, 데이터/백업 만료, 복구 매체의 위치·접근자·복구 훈련이 필요하다. 새 로더·검사기·백업·경보는 아직 없으며 M11 구현 대상으로 남긴다. 운영 시간·연락 수단·백업 매체 미확정 상태에서 상시 개시할 수 없다.

# 6. 재검토 조건

호스트 영속 비밀을 허용하지 않는 경우, root/Docker 관리자가 늘어나는 경우, 다중 호스트·외부 비밀 저장소 도입, ≤10분 복구/1시간 RPO 미달, 백업의 30일 만료를 보장할 수 없는 경우, 키 회전·보존 기간 변경 시 재검토한다.
