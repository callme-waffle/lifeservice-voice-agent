# 1. 배경 및 맥락

기존 [ADR-008](ADR-008-local-encrypted-retention.md)은 턴별 음성·최종 텍스트를 30일간 암호화 파일로 보존한다. 파일명은 무작위이며 전화번호를 저장하지 않는다. 새 요청은 AI 착신 목록의 발신자 번호 전체와 통화별 대화내역을 인증된 API에서 조회하는 것이다. 통화가 시작됐지만 발화가 없는 경우에도 수신내역은 남아야 한다. 과거 아티팩트에는 발신자 번호가 없어 소급 복원할 수 없다.

---

# 2. 검토한 대안

## A. 기존 암호화 아티팩트를 매번 전수 복호화해 목록 구성

- 장점: 새 저장 구조가 필요하지 않다.
- 단점: 발화 없는 통화와 시작·종료 상태, 발신자 번호가 없고 조회 비용이 파일 수에 비례한다.

## B. 통화별 암호화 메타데이터 아티팩트 추가

- 장점: 기존 AES-GCM 키·권한·30일 만료 정책을 재사용하고, 발화가 없는 착신도 통화 ID로 기록할 수 있다. 조회는 인증된 메타데이터와 필요한 텍스트만 복호화한다.
- 단점: 생성·종료 갱신과 프로세스 장애 시 불완전한 상태, 목록 스캔 비용을 다뤄야 한다.

## C. 별도 데이터베이스와 암호화 컬럼

- 장점: 목록·페이지 조회가 쉽다.
- 단점: 현재 단일 호스트 배포에 데이터베이스 운영·백업·접근 경계가 추가된다.

---

# 3. 결정 내용

**제안: 대안 B.** 새로운 착신부터 통화 ID, 시작·종료 시각, 상태, HT813가 SIP로 전달한 발신자 번호를 통화별 AES-GCM 아티팩트로 보존한다. [HT813 관리 안내](https://documentation.grandstream.com/knowledge-base/ht813-administration-guide/)에 따르면 `Caller ID Transport Type`에 따라 번호가 `From`, `P-Asserted-Identity`, `P-Preferred-Identity`에 실릴 수 있다. 장비의 전송 방식과 일치하는 헤더에서만 번호를 추출해 SIP 계정 ID를 발신자 번호로 오인하지 않는다. 발신자 번호가 없거나 파싱할 수 없으면 `null`로 기록한다. 번호는 신원 인증 결과가 아니라 장비가 제공한 표시 정보로 취급한다. 파일명·일반 로그·삭제 감사에는 번호를 쓰지 않는다. 아티팩트 만료는 생성 시각부터 30일이고 기존 보존 키·권한·삭제 절차를 공유한다. 목록 조회는 localhost와 Bearer 인증을 통과한 운영 API에 한정한다. 기존 텍스트 아티팩트는 통화 ID·턴 번호로 읽어 별도 대화내역 API를 만든다. 과거 통화의 번호와 통화 상태는 재구성하지 않는다.

사용자는 발신자 번호 전체 포함으로 정정했고, 이 결정안과 계획을 검토할 수 있는 상태에서 나머지 작업의 계속 진행을 지시해 저장·조회 방식도 승인했다.

---

# 4. 결정 사유

새 요구를 기존 단일 호스트·암호화 보존 구조에 맞추면서 발화 없는 통화도 기록할 수 있다. 번호를 인증된 운영 조회에만 포함해 로그와 파일 시스템 목록을 통한 노출을 막는다.

---

# 5. 결과 및 영향

## A. 쉬워지는 것

- 통화 ID로 착신 기록과 사용자·AI 대화를 연결할 수 있다.
- 기존 암호화 키와 만료 정책을 공유한다.

## B. 어려워지거나 제약되는 것

- 번호가 전달되지 않은 통화는 `null`이며, 구형 기록의 번호는 복구할 수 없다.
- 단일 파일 저장·스캔은 대량 통화 환경에서 별도 인덱스보다 느리다.
- 운영 API 토큰 보유자는 번호 전체와 대화 원문에 접근하므로 토큰 관리가 중요하다.

---

# 6. 재검토 조건

통화량 증가로 목록 조회가 느려지거나, 다중 프로세스 동시 기록·번호 보존 기간 분리·역할별 접근 통제가 요구되면 데이터베이스와 별도 키·권한 체계를 재검토한다.
