# 1. 배경 및 맥락

초기 계획은 이미 설치된 Asterisk 서버의 통화·미디어 인터페이스를 Python/FastAPI 코어의 전화 채널로 연결한다고 가정했다. 실제 설치 장비는 `192.0.2.17`의 Grandstream HT813이며 Asterisk 서버는 없다. FXO에는 외부 전화선이 연결되어 있고 FXS 전화기는 아직 없다. 화면상 두 SIP 계정은 `Not Registered`이며 과거 SIP 서버로 지정된 `192.0.2.18`도 현재 Asterisk 서버가 아니다.

사용자가 지정한 초기 통화 범위는 에이전트의 외부 회선 발신, 외부 착신의 FXS 전화기 전달, FXS 전화기의 외부 발신이다. `FXS → 에이전트`와 `외부 → 에이전트`는 후속 단계다. 사용자는 가능하면 별도 Asterisk 서버 없이 HT813에 직접 연결하기를 선호한다.

Grandstream 공식 문서는 별도 SIP 서버 없이 HT813 FXO 포트와 피어링하는 구성을 설명한다. 다만 프로젝트의 실제 SIP/RTP 상호 운용성 및 FXO·FXS 회선 점유 동작은 검증되지 않았다.

---

# 2. 검토한 대안

## A. 별도 Asterisk 서버를 설치하고 기존 승인 계획을 유지

- 장점: Asterisk가 SIP 통화 제어, 다이얼플랜 및 미디어 경계를 맡아 기존 전화 채널 계획을 사용할 수 있다.
- 단점: 현재 없는 서버의 설치·운영과 HT813 등록·연동이 선행되어 초기 발신 기능에 필요한 구성 요소가 늘어난다.

## B. 에이전트가 HT813 FXO와 직접 SIP/RTP 통화

- 장점: 현재 장비만으로 에이전트 발신 경로를 만들 수 있으며, 수신을 에이전트에 연결하지 않는 초기 범위에 맞다. 제조사 공식 자료에 SIP 서버 없는 FXO 피어링 예가 있다.
- 단점: 애플리케이션이 SIP 호출 상태, 번호 전달, RTP 오디오, DTMF, 종료·실패 복구와 접근 제어를 직접 책임져야 한다. 실제 상호 운용성은 별도 검증이 필요하다.

## C. 에이전트 전화 발신을 뒤로 미루고 FXS/FXO 로컬 전화만 사용

- 장점: 구현 범위가 작고 FXS 전화기 연결 후 로컬 통화를 먼저 점검할 수 있다.
- 단점: 사용자가 우선 지정한 에이전트 발신 기능을 제공하지 못한다.

---

# 3. 결정 내용

**결정:** 초기 전화 채널은 대안 B를 목표로 한다.

1. 에이전트의 외부 발신은 HT813 FXO(`192.0.2.17`, 화면의 로컬 SIP 포트 `5062`, UDP)를 대상으로 하는 직접 SIP/RTP 피어링으로 설계한다. 화면의 주소와 포트는 현재 관찰값이며 실제 통화 전 연결·인증·번호 전달을 검증해야 한다.
2. 외부 착신은 에이전트로 보내지 않고 HT813의 FXS 전화기 경로로 유지한다. FXS 전화기 발신도 외부 회선 경로로 둔다. 전화기 연결 전에는 관련 설정을 검증 완료로 처리하지 않는다.
3. `FXS → 에이전트`와 `외부 → 에이전트`는 초기 전화 채널 범위에 넣지 않는다.
4. 대체되는 ADR-001/002의 Python/FastAPI 코어, 단일 컴포넌트의 모듈형 모놀리스 및 `apps/orchestrator` 배치는 그대로 채택한다. `contracts`는 구현에 의존하지 않고, `core`는 `contracts`에만 의존하며, `adapters`와 `channels`는 `core` 내부나 서로의 모델 구현을 직접 참조하지 않는다. 구체 구현의 조립·수명 주기는 `bootstrap`이 맡는다. 모든 스트림에 세션 ID·순서·오디오 형식·취소·오류 의미를 보존하고, 코덱 변환은 채널과 `infrastructure/audio`가 담당한다. 비동기 큐의 크기·역압·시간 제한·자원 정리 계약도 유지한다. 전화 채널 디렉터리는 `channels/ht813`으로 바꾸고 대응 테스트·배포 계획은 별도 대체 계획에서 정한다.
5. 장비 설정 변경, 실제 발신 및 실전화 통합 테스트는 수정 계획의 검증 절차와 기존 Gate 2 조건을 따른다.

이 결정은 사용자 승인으로 ADR-001/002를 대체한다. 구현은 별도 대체 계획의 승인 후 진행한다.

---

# 4. 결정 사유

현재 존재하는 장비만으로 사용자가 우선 요구한 에이전트 발신 경로를 구현할 가능성이 있으며, Grandstream은 HT813 FXO의 직접 피어링 절차를 공개한다. 에이전트 수신을 뒤로 미루면 초기 전화 채널에서 SIP 등록 서버와 수신 라우팅을 구현할 필요가 줄어든다.

FXS의 편한 외부 발신과 착신 전달은 HT813의 로컬 회선 기능을 이용하는 후보가 있지만, `Life Line Mode=Always Connected`는 제조사 문서에서 VoIP 호출을 허용하지 않는다고 설명한다. 이 모드를 에이전트의 FXO 발신과 공존 가능한 것으로 가정하지 않는다. `PSTN Ring Thru FXS` 및 `Route Call to PSTN`의 조합과 회선 점유를 실제 장비에서 별도 검증한다.

---

# 5. 결과 및 영향

## A. 쉬워지는 것

- 초기 전화 발신 경로에서 별도 Asterisk 서버의 설치와 운영을 선행 조건으로 두지 않는다.
- 현재 FXO에 연결된 외부 회선을 에이전트 발신 대상으로 삼을 수 있다.
- 에이전트 수신 및 FXS에서 에이전트 호출은 후속 단계로 분리된다.

## B. 어려워지거나 제약되는 것

- 애플리케이션이 SIP/RTP 경계의 신뢰성, 미디어 변환 및 전화번호 권한 정책을 직접 구현·검증해야 한다.
- 한 개의 외부 회선을 FXS 전화기와 에이전트가 공유하므로 동시 사용·통화 중 응답 정책이 필요하다.
- FXS 전화기 미연결 상태에서는 외부 착신과 FXS 발신을 검증할 수 없다.
- 승인된 Asterisk 채널 계획과 해당 전화 부분 ADR을 수정·재승인해야 한다.

---

# 6. 재검토 조건

- HT813 직접 SIP/RTP 상호 운용성 또는 번호 전달이 실제 장비에서 요구사항을 충족하지 못하는 경우
- 동시 통화, 복잡한 다이얼플랜, 착신 분기 또는 다수 장비 등록이 필요한 경우
- 에이전트가 외부 착신을 받거나 FXS 전화기에서 에이전트를 호출하는 후속 요구가 시작되는 경우
- 별도 Asterisk 서버를 운영하기로 사용자가 결정하는 경우
